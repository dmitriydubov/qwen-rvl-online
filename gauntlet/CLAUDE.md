# Gauntlet: как здесь ведётся разработка

Код пишет агент. Человек код не читает: он читает спецификацию (Gherkin), отчёт о гейтах и изменения
самого набора `gauntlet/`. Итоговое решение по каждой задаче принимает человек — merge PR в GitHub.
Работа считается сделанной только когда `./gradlew gauntlet` зелёный, ветка запушена и PR открыт.
Никогда не сообщай об успехе, не выполнив проверку.

## Репозиторий
Монорепозиторий сервисов, за которые отвечает владелец; у каждого сервиса своя Gradle-сборка
в своём каталоге, корневой сборки нет и не будет. Набор `gauntlet/` один на все модули и работает
только во внешнем контуре — в облаке Claude Code и в GitHub (см. «Правила владельца», «Рабочий контур»).

| Каталог | Что это | Под гейтами |
|---|---|---|
| `data-reference/` | сервис справочных данных: справочники и полисы из 1С:УСК (RabbitMQ), REST-чтение для соседних сервисов; пакет `ru.projectx.datareference` | да (`module=data-reference`) |
| `contract-service/` | сервис Договоров, он же бэкенд ЛК застрахованного: договоры КМ и полисы ЛМ по задачам сервиса Заявок, обмен с 1С:УСК, печатные формы, акцепт; пакет `ru.projectx.contracts`; правила — `contract-service/CLAUDE.md`, план — `docs/gauntlet-plan-contract-service.md` | да (`module=data-reference,contract-service`, с 2026-10-12) |
| `project_files/` | ТЗ, схемы и структуры данных — источники предметной области (раздел «Источники документации»). Разложен по сервисам: `common/` — документы контура целиком и соседей, `data-reference/` — документы справочного сервиса, `contract-service/` — документы сервиса Договоров (контракты с Заявками и 1С, ТЗ ЛК, Ordering; до 2026-10-07 лежали в `contract-service/project_files/` и корне `project_files/`) | — |

Сервис Заявок (он же сервис HR), BFF и фронтенд пишут другие разработчики в своих репозиториях.
Правила и предметная область `data-reference` (контракт 1С:УСК, пакеты, транзакции, ПДн, тесты) описаны
в `data-reference/CLAUDE.md` — прочитай его перед задачей в `data-reference`. Он главный по предметной
области и правилам кода. Фичи, написанные до 2026-10-07, ссылаются на него по старому пути
`contract-service/CLAUDE.md`: разделы те же, шапки фич не переписываются. По процессу, веткам, проверкам перед коммитом, репозиториям сборки, тестовой
инфраструктуре и лимитам размера главный этот файл: там, где тот расходится (фиксированная ветка разработки,
`./gradlew build` как проверка, метод до 40 строк), действует gauntlet.

## Гейты

| Команда | Что проверяет |
|---|---|
| `./gradlew gauntletFast` | integrity (нет отключённых тестов и подавлений) → Checkstyle (размер, структура, CC ≤ 3) → PMD (антипаттерны) → unit-тесты → архитектура (ArchUnit) → перепись тестов (каждый тестовый класс, который скомпилировали `test` и `archTest`, запущен) → приёмка (Cucumber, ни одного skipped) → CRAP ≤ 8 → дубли |
| `./gradlew mutationGate` | PIT по изменённым классам: каждый покрытый мутант убит (test strength 100 %), покрытие строк мутируемых классов ≥ 80 %; мутант RUN_ERROR (JVM тестов упала на `redefineClasses`, обычно на record; PIT считает его обнаруженным) убитым не засчитывается — только по строке `gauntlet/config/pit-runerror-allowlist.txt`, которую человек добавил, прочитав тесты |
| `./gradlew gherkinMutation` | каждое значение из Examples мутируется по очереди; сценарий обязан упасть в шаге (выжил — step игнорирует значение). Контроли — та же строка без изменений до мутантов (`cN`) и после них (`zN`) — обязаны пройти: красный контроль (`MUTANT ERROR cN/zN control …`) значит, что сценарий не исполняется сам по себе (зависит от соседнего сценария, от фикстуры, от своего имени; `zN` — строку нельзя повторить на одном стенде) — чини независимость сценария (`@Before`, сбрасывающий состояние), а не step-определения; если нужна правка самой фичи — это вопрос к человеку |
| `./gradlew gauntlet` | всё вместе |

Область проверки — diff относительно базовой ветки плюс незакоммиченные файлы (`baseRef` в
`gauntlet/config/gauntlet.properties`). Если там задан `module` (монорепозиторий; может быть списком),
Gradle-сборки живут в этих каталогах: `./gradlew …` запускай из каталога модуля (`cd core && ./gradlew …`),
`src/` и `build/` — его, фичи — в `<module>/src/acceptanceTest/resources/features/`, настройки модуля —
в `gauntlet/config/<module>/` (`./gradlew gauntletInfo` покажет, что подхватилось), а `gauntlet/` остаётся
в корне. Задача, затрагивающая два модуля, — одна спецификация (фичи в обоих) и один PR. Stop-хук сам
запускает `gauntletFast` в каждом модуле, где ход менял код, и возвращает тебе падения. `--continue`
показывает все красные гейты за один прогон. Отчёты: `<module>/build/reports/`.

**Среда и обязательная самонастройка в начале сессии.**
- Тесты с базой и брокером (интеграционные и приёмка) поднимают контейнеры через Testcontainers. Без Docker они **падают, а не пропускаются** — так задумано. В облачной
  VM демон поднимает SessionStart-хук (`dockerd` напрямую: `service docker start` там падает на ulimit),
  строка статуса показывает `docker: up`. Перед первым запуском сборки или тестов проверь `docker info`: если команды `docker` нет или демон не отвечает, **проведи настройку сам без остановки на вопрос человеку** — проверь доступные рантаймы (системный `dockerd`, Docker Desktop, Colima, rootless Docker); если в Linux-среде `docker` не установлен и есть права установки пакетов (`apt-get` от `root` или `sudo -n apt-get`), установи `docker.io` (`DEBIAN_FRONTEND=noninteractive apt-get update && apt-get install -y docker.io`); подними демон (`nohup dockerd --host=unix:///var/run/docker.sock > /tmp/dockerd.log 2>&1 &`, при ненулевом UID — через `sudo -n` с правом группы `660` на `/var/run/docker.sock`) и дождись `docker info`. Если `docker info --format '{{.CgroupDriver}}'` печатает `none` (или `docker pause` отвечает `freezer not supported` в контейнерной среде без cgroup freezer), подними штатный сокет-прокси набора `nohup python3 -I -B gauntlet/hooks/docker_pause_shim.py /tmp/docker-pause-shim.sock >/tmp/docker-pause-shim.log 2>&1 &`, перезапусти демон Gradle (`./gradlew --stop`) и запускай прогоны с `DOCKER_HOST=unix:///tmp/docker-pause-shim.sock` без изменения файлов репозитория. Если в облачной 2-vCPU VM контейнер `rabbitmq:*-alpine` падает на старте с `OS monotonic time stepped backwards!`, собери локальный двухстрочный образ-переопределение с `ENV ERL_AFLAGS="+c false"` под тем же тегом без правки файлов репозитория. Красный Stop-хук из-за «Could not find a valid Docker environment» — это окружение, а не код.
- Проверь версии Java из `gauntlet/config/gauntlet.properties` (`project.java.version`, `gate.java.version`): если `java -version` или `JAVA_HOME` указывают не туда или не заданы, найди установленную JDK в стандартных каталогах (`/usr/lib/jvm`, `~/.jdks`, `~/.sdkman`, кэш Gradle toolchains, `/workspace`) либо при наличии прав пакета установи `openjdk-<версия>-jdk` и экспортируй `JAVA_HOME` и `GAUNTLET_GATE_JAVA_HOME`. Обращаться к человеку по поводу Docker или JDK допустимо **только** если проверены все доступные способы и среда физически не даёт ни прав установки, ни запуска демона (вывод команд приложи в «Не проверено»).
- Maven Central через прокси иногда отвечает 429 (Too Many Requests) на пачку новых артефактов: повтори
  через 20–60 секунд, к коду это отношения не имеет.
- Набор подключается к сборке только при публичных репозиториях — свойство `publicRepositories`, по умолчанию
  выключено (Nexus контура). В облаке Claude Code SessionStart-хук пишет `publicRepositories=true` в
  `~/.gradle/gradle.properties` (`$GRADLE_USER_HOME`; заданное там значение не трогает, а не `true` — предупреждает),
  Stop-хук при `CLAUDE_CODE_REMOTE=true` передаёт Gradle `ORG_GRADLE_PROJECT_publicRepositories=true` сам, в GitHub Actions —
  `env` задания в `gauntlet.yml`. В локальной сессии и в других агентных средах задай `ORG_GRADLE_PROJECT_publicRepositories=true`
  (или впиши `publicRepositories=true` в `~/.gradle/gradle.properties`), иначе сборка пойдёт в Nexus контура, а Stop-хук
  не найдёт задач набора.
- Не заканчивай ход, пока идёт фоновый прогон гейтов: Stop-хук запустит свой в тот же `build/` и будет ждать
  его конца (блокировка `.gradle/gauntlet-build.lock`, до 1500 с), а при более долгом прогоне упадёт по таймауту.

## Процесс для задачи, меняющей поведение сервиса

Триггер — сообщение пользователя: новая фича, багфикс, изменение контракта или сообщения. Для правок,
не меняющих поведение (рефакторинг, зависимости, логи, инфраструктура), шаги 2–4 пропускаются,
остальное так же.

1. **Контекст и окружение.** Прочитай `gauntlet/config/gauntlet.properties`, настройки модуля в
   `gauntlet/config/<module>/` (`gauntlet.properties`, `architecture.properties`), правила модуля
   (его `CLAUDE.md` и документы предметной области из раздела «Источники документации») и существующие фичи по теме в
   `<module>/src/acceptanceTest/resources/features/`. Убедись, что готовы Docker (`docker info`), нужная JDK (`JAVA_HOME`, `GAUNTLET_GATE_JAVA_HOME`) и публичный режим сборки (`ORG_GRADLE_PROJECT_publicRepositories=true` вне облака Claude Code и CI), при необходимости настрой их сам по блоку «Среда и обязательная самонастройка» выше.
2. **Спецификация.** Делегируй сабагенту `specifier`: запрос дословно, релевантные фичи, ограничения из
   сообщения. Он вернёт изменённые файлы, по строке на сценарий, открытые вопросы и допущения. У каждого допущения
   о протоколе или фреймворке — источник версии сборки (`gauntlet/subagents.md`, карточка 4.2): версия и как
   получена, источник, цитата; без него допущение — «не проверено» и открытый вопрос. Спецификации пишутся
   на русском (`# language: ru`); в рабочий контур они не переносятся.
   Если задача выбирает значение или версию из нескольких (история строк, эхо, повтор, отказ, удаление,
   очистка поля), specifier дополнительно возвращает **таблицу решений**: тип события × наблюдаемый исход
   (отправленное сообщение, сохранённое состояние); каждая строка таблицы — сценарий со значениями в
   Examples. Правило выбора, которое не закреплено ни сценарием, ни явным «Вне фичи», — открытый вопрос
   владельцу до заморозки, а не место для решения кодом.
3. **Утверждение — остановись.** Покажи пользователю пути файлов, по одной строке на сценарий, вопросы и
   допущения specifier'а. Спроси, утверждает ли он спецификацию, и закончи ход. До ответа — никакого кода
   и никаких коммитов: незакоммиченные фичи — черновик, который человек ещё может править (Stop-хук их не
   гоняет). Stop-хук облачной платформы (`~/.claude/stop-hook-git-check.sh`, не gauntlet) один раз
   заблокирует остановку и попросит закоммитить и запушить изменения — черновик фич не коммить: ответь
   одной строкой, что ждёшь утверждения, и остановись повторно, вторая остановка проходит. Решения,
   нужные от человека, выводи нумерованным списком, чтобы он ответил «1) да 2) да …», и к каждому пункту ставь
   рекомендацию «ответьте здесь» или «переслать координатору» («Правила владельца»). Просят изменений —
   снова к `specifier`.
   **Дыра-чек перед заморозкой:** каждое правило, которое код должен решать (выбор версии, порядок строк,
   судьба отказа, явная очистка поля против его отсутствия), закреплено сценарием или явно вынесено
   «Вне фичи» с принятым риском. Критерий — наблюдаемость приёмкой: меняется хоть одно свойство, которое
   видит приёмка (ответ, сообщение, сохранённая строка), — правило обязано быть в спецификации. Дыра —
   вопрос владельцу до заморозки; после заморозки она стоит уже правки спецификации человеком.
   Если в `gauntlet.properties` стоит `spec.approval=pr`, не останавливайся: человек прочитает Gherkin в PR.
4. **Заморозка и непрерывный переход к реализации.** Ответ человека с утверждением спецификации («да», в том числе вместе с ответами «1) … 2) …» по списку шага 3) — это прямая команда выполнить **весь оставшийся маршрут шагов 4–8 вплоть до открытого PR в этом же ходе без повторной остановки**. Закоммить только фичи отдельным коммитом `spec: <что описано>`, сразу запушь ветку (`git push -u origin HEAD` — с этого момента спецификация видна человеку на GitHub, а хук замораживает её для всех агентов) и **немедленно, не заканчивая ход, переходи к шагу 5**. Завершать ход после коммита `spec:` с сообщением «спецификация заморожена, жду команды продолжать» запрещено (Stop-хук запускает полный `gauntletFast` уже на закоммиченной спецификации и не выпускает ход на красной приёмке); остановиться после шага 4 допустимо только по основаниям раздела «Когда застрял», на находке типа «правило» (шаг 7) или по правилу «Лимит токенов». Если по ходу реализации спецификация окажется противоречивой или невыполнимой — остановись и опиши проблему; не подгоняй ни код, ни тесты, ни спецификацию.
5. **Реализация (ты).** TDD маленькими шагами по правилам ниже; step-классы в `src/acceptanceTest/java`.
   `./gradlew gauntletFast --continue` до зелёного.
6. **Закалка.** Сабагент `hardener` (название фичи и список изменённых классов): убивает выживших мутантов
   и пустые step-определения, правит только тестовый код. Его предложения по продакшен-коду применяй
   сам, затем снова `gauntletFast`. Если PIT нечего мутировать (правка только конфигурации), ручные мутанты
   hardener предлагает списком, а применяешь, гоняешь тесты и откатываешь их ты — и перед коммитом проверяешь,
   что `src/main` чист. Его числа сверь с выводом гейта: строки итога `./gradlew mutationGate` (`PIT summary: …`,
   `mutationGate: …`) первого и последнего прогона и мутант на каждый добавленный тест (`gauntlet/subagents.md`,
   карточка 4.5).
7. **Ревью.** Сабагент `reviewer` (базовая ветка, фичи, список изменённых файлов). Его итог — не факт, пока ты
   его не принял (`gauntlet/subagents.md`, карточка 4.5): открой `file:line` каждой находки и сверь цитату, повтори
   команды воспроизведения, которые ничего не меняют; APPROVED принимается только со строкой
   «Осмотрено: файлы диффа N из N», и её число и список совпадают с твоим M — той же командой в дереве сессии:
   `git diff --name-only $(git merge-base <база> HEAD)` и `git ls-files --others --exclude-standard`. Ревьюер
   внешним маршрутом читает копию на коммите: перед его ревью и перед каждым следующим раундом закоммить работу
   без push (`gauntlet/subagents.md`, п. 5.6). Возврат за доказательствами — не раунд: в доработке — только
   доказательства к прежним находкам, новая находка идёт в следующий раунд, если он остался. Каждая находка
   помечается типом: **«дефект»** — поведение противоречит утверждённой спецификации или решению владельца,
   правится в коде; **«правило»** — спецификация не определяет поведение, которое код решает (выбор версии,
   порядок, судьба отказа, очистка против отсутствия). Находки типа «правило» не уходят в новый раунд
   правок: они идут владельцу нумерованным списком «ответьте здесь», работа над ними останавливается до
   ответа; после ответа правило закрепляется в спецификации (замороженные фичи правит только человек или
   его делегат), затем один проход реализации против всего правила. Исправь все blocker/major типа
   «дефект», повтори прогон, верни результат ревьюеру. **Не больше 2 раундов**; после второго
   CHANGES REQUESTED с непогашенными находками остановись и опиши остаток, а не начинай третий круг.
   Рекомендация противоречит утверждённой спецификации — вопрос человеку.
8. **Финал.** `./gradlew gauntlet --continue` зелёный → коммит → `git push` своей ветки → открой PR
   (`gh pr create`, в описании — отчёт ниже; если не получилось, скажи об этом: пользователь нажмёт
   Create PR сам). Тот же отчёт — в чат. **Никогда не мержи** и не проси мержить за тебя: merge — это
   утверждение результата человеком. Одна задача — одна ветка и одна сессия: следующую задачу человек
   начинает новой сессией от основной ветки.

### Отчёт (в PR и в чат)
- **Гейты**: каждый со статусом; max CRAP; мутанты — убито / выжило / без покрытия; Gherkin-мутанты.
- **Спецификация**: файлы и сценарии — то единственное, что человек читает.
- **Ревьюер**: вердикт, раунды, что исправлено; находки типа «правило» — отдельным списком с пометкой,
  что они ждут решения владельца, и что по ним правок кода не было.
- **Сабагенты**: маршрут, число карточек, сколько отчётов возвращено и не принято.
- **Сверка по документации**: по строке на решение, которое опирается на поведение фреймворка, библиотеки
  или протокола: утверждение → источник (URL или jar и класс) → версия; отдельно — что проверено только
  по байткоду и почему.
- **Перенос в контур**: новые зависимости и плагины с координатами (group:artifact:version) для проверки
  в корпоративном реестре; удалённые и переименованные файлы и классы; новые переменные окружения и значения
  по умолчанию (см. «Правила владельца»).
- **Нужно решение человека** — нумерованным списком, у каждого пункта — «ответьте здесь» или «переслать
  координатору» («Правила владельца»): эквивалентные мутанты, предлагаемые исключения,
  вопросы к спецификации, правила выбора вне спецификации (находки типа «правило»).
- **Оценка**: трудозатраты задачи для Jira против факта, с причиной расхождения.
- **Остаточные риски**.

### Правила владельца
- **Задача для Jira** — это задача владельца в рабочем контуре, а не задание сессии. Координатор пишет её в свой чат
  простым человеческим языком, без «нейрослопа» (тема, что и зачем, критерии приёмки, трудозатраты) до начала работы;
  после апрува владельца координатор открывает сессию шага с отдельным описанием уже для сессии. Если задача пришла
  сессии в промпте, заново она не пишется.
- **Внешний независимый ревьюер** — ИИ-ревьюер, которого выбрал владелец, — читает каждый PR и сам ничего не правит.
  Его замечания приходят в PR комментариями: от бота, подключённого к репозиторию, или с аккаунта владельца. Вендора
  и модель владелец может сменить, ревьюеров может быть несколько: правило касается каждого.
  Комментарий ревьюера — не истина и не шум: автор PR (сессия шага — на своём PR, координатор — на своём) проверяет
  каждое замечание по коду и источникам; прав — исправить и запушить; не прав — ответить в том же треде, почему, со
  ссылкой на код или документацию. Молчать нельзя. Замечание, противоречащее утверждённой спецификации или решению
  владельца, — вопрос владельцу, а не правка. Каждый ответ в GitHub начинается строкой
  «Ответ Claude Code на комментарий <ревьюер>» с номером или датой комментария, чтобы в треде было видно, кто кому
  отвечает. Ревьюер назван так, как подписано замечание: имя бота или, если ревью пришло с аккаунта владельца, имя
  ревьюера из текста ревью. Подписи нет — имя не угадывать, строка ответа тогда
  «Ответ Claude Code на комментарий внешнего ревьюера». Неясно, ревью это или решение самого владельца, — вопрос
  владельцу.
- **Модель и уровень рассуждений сессий.** Координатор — Fable 5.1, уровень max,
  ультракод выключен: воркфлоу из многих агентов (adversarial-проверка PR, параллельная сверка плана) — только по
  явному запросу владельца. Сессии шагов по умолчанию — Opus 5.5, уровень xhigh, без ультракода: процесс gauntlet
  уже многоагентный (specifier, hardener, reviewer, хуки), ультракод поверх него — главный расход лимита. Шаги с
  тонкой семантикой фреймворка (транзакции, Hibernate, AMQP, таймауты) — Fable 5.1 xhigh. При старте каждой сессии
  шага координатор пишет в чат рекомендацию модели и уровня под эту задачу с обоснованием; решает владелец. При
  создании сессии координатор задаёт только модель; уровень и ультракод владелец выставляет в настройках сессии.
- **Сабагенты и их маршрут.** Правило тщательности, приёмка отчётов, карточки и маршрут — в `gauntlet/subagents.md`:
  читай его, когда запускаешь сабагента или принимаешь его отчёт. Итог сабагента — не факт, пока ты его не принял
  по доказательствам. Карточки только для чтения исполняет роль `checker`, а не форк и не Explore: у неё права
  `reviewer` — ни файлов, ни состояния git, ни `git worktree add`; сборку она гоняет в worktree, временный файл
  пишет в клоне вне репозитория по пути, который видит guard (`gauntlet/README.md`, раздел 9), — оба создаёт тот,
  кто её запускает. Кто исполняет карточки (свои, CLI другого вендора или вручную через владельца), решает владелец:
  `subagents.route` в `gauntlet/config/gauntlet.properties`; при `ask` — один вопрос на задачу пунктом списка решений
  вместе с задачей для Jira, и пред-проверка начинается после ответа. Маршрут ревьюера сессии шага координатор пишет в
  её промпт, и сессия заново не спрашивает; сессия без маршрута в промпте при `ask` не спрашивает: её сабагенты —
  свои. Пишущие роли — specifier, hardener, кодер — всегда свои.
- **Решения человека — нумерованным списком** в любой остановке и в отчёте; ответ «1) да 2) нет …»
  записывается в описание PR.
- **Какие вопросы сессия шага адресует координатору.** Сессия шага решает только свою
  задачу; к каждому пункту списка решений она ставит рекомендацию: «ответьте здесь» или «переслать координатору». Владелец
  пересылает вопрос в чат координатора, а сессия до ответа работает дальше там, где от него не зависит. Переслать
  координатору: всё, что меняет план за пределами шага (состав, оценки или порядок других шагов, новый шаг, перенос
  остатка в другой шаг); правки набора gauntlet и его файлов (`gauntlet/`, `.claude/`, любой `CLAUDE.md`, политика
  архитектуры, allowlist'ы, исключения из PIT, эквивалентные мутанты); контракты с соседними сервисами и внешними системами и
  вопросы к их разработчикам; дефекты и долг, найденные вне файлов шага; модель, уровень рассуждений и лимиты; всё, что
  затрагивает другую идущую сессию или цепочку общих файлов. Владелец отвечает сам: выбор варианта спецификации и
  критериев приёмки своего шага, бизнес-правила из ТЗ в объёме шага, утверждение спецификации, допустимые остаточные риски
  шага, замечания внешнего ревьюера, противоречащие спецификации или решению владельца. Если вопрос не попадает ни в
  один список, сессия предлагает «переслать координатору».
- **Лимит токенов.** Если в сессию пришло предупреждение о 99 % пятичасового или недельного лимита либо
  человек написал «пауза», работа ставится на паузу, 100 % не ждать: закоммить и запушь свою ветку, напиши
  статус (что сделано, что красное, что дальше). Красный гейт на паузе не чинится: отвечай Stop-хуку одной
  строкой «пауза по лимиту, работа не сделана». Возобновляет человек или координатор сообщением в сессию.
- **README модуля** (решение владельца 2026-10-17, правило то же, что в medius). README — короткий вход в сервис для
  эксплуатации, остальное — в `<module>/docs/`.
  - Пишет и меняет README только координатор модуля. Сессия шага README не правит: если её изменение делает README
    неверным (новая очередь, таймаут, переменная, таблица), она называет это в отчёте пунктом «переслать
    координатору», и координатор правит README после мержа.
  - Не больше 3500 символов (Unicode, переводы строк LF; код, таблицы и разметка входят). Пока длину не проверяет
    `integrityCheck` (правка набора придёт из medius), её проверяет `reviewer` и координатор:
    `python3 -c 'import sys; print(len(open(sys.argv[1], encoding="utf-8").read()))' <module>/README.md`.
  - Разделы по порядку: стек; о сервисе (2–3 строки); таймауты (что, значение, переменная); поведение при
    недоступности внешних систем и работа без них; получение и отправка сообщений (очереди, REST); диагностика по
    базе (таблицы, статусы, три SQL-запроса только на чтение, без персональных данных); ссылки на `docs/`.
  - `<module>/docs/design.md` — причины решений («почему так устроено»): ловушка, которую легко «упростить»,
    ограничение фреймворка, правило соседа, порядок, транзакция, персональные данные; простым языком, с именем
    класса; пересказ кода не пишется. Причину вводит та задача, которая вводит решение, в том же PR — это делает
    сессия шага. `<module>/docs/operations.md` — процедуры эксплуатации: сборка и образ, локальный запуск, все
    настройки и переменные окружения, метрики и когда тревожиться, ручные операции, которые меняют данные или роль
    экземпляра. `<module>/docs/troubleshooting.md` (решение владельца 2026-10-27) — известные проблемы эксплуатации:
    признак, как проверить (здоровье, метрики, журнал, запросы к базе только на чтение и без персональных данных) и
    что делать; операции, которые меняют данные, — ссылкой на `operations.md`. README ссылается на него в «ссылках на
    `docs/`».
  - Причины, нужные только приёмке и сборке с гейтами, — в `<module>/src/acceptanceTest/README.md` (в контур не
    уходит).
  - Каждое утверждение о фреймворке или библиотеке сверяется с источником по правилу 12; неподтверждённое
    снимается. Устаревшее не оставляется и не помечается: пишется так, как в коде, расхождение называется в отчёте
    PR. Следов разработки нет (правило 15, проверка — «Рабочий контур»).
- **Рабочий контур** — закрытая сеть компании, где живут сервисы. Там нет GitHub, интернета и Claude:
  облачные сессии Claude Code и GitHub — внешний контур. Зависимости и образы в контуре берутся только из
  корпоративного Nexus, с ним владелец работает сам, вручную; правки переносит тоже вручную, PR за PR
  в порядке мержа. Из сессии Nexus закрыт, и обращаться к нему не нужно: здесь — только публичные адреса
  (Maven Central, портал плагинов Gradle, Docker Hub, официальная документация). *Внешний контур* — где владелец
  пишет запросы Claude и работает с GitHub (облачные сессии Claude Code, GitHub Actions): зависимости публичные и
  берутся напрямую, не через Nexus. Поток: PR в GitHub → merge владельцем → владелец вручную переносит файлы
  сервиса в рабочий контур → прогон там.
  - **Сборка в обоих режимах.** Модуль обязан собираться и работать и с Nexus, и с публичными репозиториями: в
    сессии проверяется публичный режим, режим Nexus — у владельца при переносе. Поведение, которое проверяется
    только во внешнем контуре (приёмка, гейты), не должно быть нужно для работы и сборки в рабочем. Никаких
    обращений к GitHub и интернету в рантайме и в сборке по умолчанию. В переносимых файлах не упоминать Claude
    и Anthropic: ни в именах, ни в переменных окружения, ни в комментариях.
  - **Gradle Wrapper.** В рабочем контуре `./gradlew` запускается напрямую, а дистрибутив Gradle туда доставляется
    вручную, поэтому версию Gradle Wrapper (`distributionUrl` в `<module>/gradle/wrapper/gradle-wrapper.properties`)
    и сам wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper/`) не менять без согласования с владельцем; нужна
    смена — вопрос в «Нужно решение человека» («переслать координатору»).
  - **Проверка следов разработки** (правило 15) — вывод обеих команд (содержимое и имена файлов) идёт в отчёт
    «Перенос в контур»: `{ [ "$(LC_ALL=C.UTF-8 locale charmap)" = UTF-8 ] || echo 'ОШИБКА: нет локали C.UTF-8';
    LC_ALL=C.UTF-8 git grep -n -I -i -P 'claude|anthropic|antigravity|gemini|codex|grok|kimi|qwen|github|pull request|\bPR ?#[0-9]+|решени[еяю] владельца|(?<![\p{L}\p{N}_])шаг\p{L}* [0-9]+\p{L}?(?![\p{L}\p{N}_])'
    -- data-reference contract-service ':!*/CLAUDE.md' ':!*/src/acceptanceTest/*' ':!*/gradlew' ':!*/gradlew.bat'
    ':!*/gradle/wrapper/*'; [ $? -le 1 ] || echo 'ОШИБКА: git grep не выполнился'; } | grep -v -i 'com\.github\.'` и
    `git ls-files -- data-reference contract-service ':!*/CLAUDE.md' ':!*/src/acceptanceTest/*' | grep -i -E
    'claude|anthropic|antigravity|gemini|codex|grok|kimi|qwen'` (строки команд склеиваются в одну). В контур переносятся каталоги сервисов, поэтому команды
    смотрят только их. Шаблон первой — PCRE в локали C.UTF-8: в локали C ERE сравнивает кириллицу побайтно и её не
    находит (команда молча отвечает пустым выводом), а в C.UTF-8 `[а-я]` в ERE роняет `git grep`; границу слова у
    кириллицы задают `(?<![\p{L}\p{N}_])` и `(?![\p{L}\p{N}_])`, а не `\b`. Строка `ОШИБКА` в выводе значит, что
    проверка не выполнена, — это не «0 строк». `-I` пропускает двоичные файлы; Gradle Wrapper исключён: его
    генерирует Gradle и он не меняется (см. выше); пакеты `com.github.*` — координаты библиотек (Caffeine), а не
    следы. Слово «gauntlet» команда не ищет — его содержит код подключения набора в `settings.gradle` и
    `build.gradle`; комментарии о наборе ловит `reviewer`. Строки, которые уже есть в основной ветке, — долг, он
    чистится отдельной задачей: сравни вывод с основной веткой, новых строк быть не должно (на 2026-11-09 вывод
    обеих команд на основной ветке пуст).
  - Репозитории выбирает свойство `publicRepositories` (`settings.gradle` модуля): по умолчанию — Nexus контура,
    со свойством `true` — публичные; во внешнем контуре его выставляют хуки набора и `gauntlet.yml`, сам
    `settings.gradle` облако и GitHub не упоминает. Набор gauntlet подключается, только когда рядом лежит
    `gauntlet/` и репозитории публичные. Переключатель и закомментированный вариант «только Nexus» не трогай.
  - В контур не переносятся `gauntlet/`, `.claude/`, `.agents/`, `CLAUDE.md` и `GEMINI.md` (корневые и модулей), `.github/`,
    `<module>/src/acceptanceTest/`, `project_files/` и корневой `docs/` (планы серий и заметки координаторов).
    Продакшен-код и unit-тесты от них не зависят, а сборка модуля без них зелёная. Каталог `<module>/docs/`
    (`design.md`, `operations.md`, `troubleshooting.md`) — документация сервиса: переносится вместе с модулем, следов
    разработки в нём нет (решение владельца 2026-10-17).
  - Каждая новая зависимость и плагин — в отчёт с координатами `group:artifact:version`: владелец проверит
    их в Nexus до переноса. Известно, что Nexus контура отдаёт `spring-boot-starter-web`, но не
    `spring-boot-starter-webmvc` и `spring-boot-starter-webmvc-test` (см. `data-reference/build.gradle`);
    такие ограничения не обходить.
  - Удалённые и переименованные файлы — отдельным списком в отчёте: при ручном переносе старые файлы
    удаляются, иначе останутся дубли классов и бинов. Переносы и переименования — только когда они нужны
    задаче.
  - Новые переменные окружения и изменённые значения по умолчанию — в отчёт.
  - Реестр образов в коде не хардкодится: в облаке образы Testcontainers идут с Docker Hub, в контуре
    префикс реестра задаёт его CI (`TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`).

## Жёсткие правила
1. **Не трогай gauntlet.** `gauntlet/`, `.claude/`, `CLAUDE.md`, `.github/workflows/gauntlet.yml` и
   `.github/workflows/gauntlet-kit.yml` принадлежат человеку, как и то, что другие агентные инструменты читают как
   свои инструкции, роли и настройки: `AGENTS.md`, `AGENTS.override.md`, `GEMINI.md`, `QWEN.md`, `.codex/`,
   `.gemini/`, `.agents/`, `.grok/`, `.kimi-code/`, `.qwen/`, `.qwenignore`, `.agentignore`, `.aiignore`,
   `.mcp.json` (хук блокирует правки, CI-проверка `gauntlet kit unchanged` красная на PR, который их меняет). Вне
   репозитория так же охраняются настройки агентов пользователя: `~/.claude`, `~/.codex`, `~/.gemini`, `~/.agents`,
   `~/.grok`, `~/.kimi-code`, `~/.qwen`, `~/.env`, `/etc/codex`, `/etc/grok`, `/etc/qwen-code`. Если проверка
   выглядит неверной — остановись и объясни, не обходи её.
2. **Никогда не ослабляй проверку ради зелёного**: никаких `@Disabled`/`@Ignore`/assumptions, `@Generated`/
   `@DoNotMutate`, `CHECKSTYLE:OFF`/`NOPMD`, фильтров тестов, `enabled = false` или переконфигурации гейтов
   в build-скриптах, удалённых или ослабленных assert'ов. `integrityCheck` это ловит; человек видит каждую
   попытку в diff. `INTEGRITY T6 <путь>  compiled but not run by test  |  <класс>` значит, что-то не пускает
   этот класс в прогон: фильтр в скрипте сборки или в тестовых ресурсах, движок, которого нет у задачи, TestNG
   `enabled = false`, пропущенная задача тестов (`onlyIf`, `enabled = false`); `… not compiled for test` — исходник
   оставлен вне компиляции (exclude у source set или у задачи компиляции); `gauntlet: :test is not part of this
   build` — задачу убрали из сборки (`-x`, `excludedTaskNames`). Убери причину; allowlist — у человека.
   `gauntlet: Gradle finished … without running …` значит, сборка оставила задачу гейта вне прогона
   (`gradle.startParameter.excludedTaskNames`, набор не подключён), выключила или пропустила её (`enabled = false`,
   `onlyIf`); `… ended with exit value …, and the build ignores exit values` — сборка прячет вердикт инструмента
   (`ignoreExitValue`). Верни, как было.
3. **Фичи — это спецификация** (`<module>/src/acceptanceTest/resources/features/`, на русском,
   `# language: ru`). Пишет их только сабагент `specifier`, утверждает только человек — в чате. Код должен удовлетворять спецификации, а не наоборот.
4. **TDD.** На каждое поведение: сфокусированный падающий unit-тест, который упал бы на правдоподобной
   неверной реализации → минимум кода → рефакторинг. Приёмочные тесты не заменяют unit-тесты.
5. **Маленькие функции.** Цикломатическая сложность ниже 4 (Checkstyle: CC ≤ 3, NPath ≤ 20); CRAP-гейт
   падает выше 8. Дели методы со смешанными обязанностями; извлечённый метод сам владеет своими входами —
   не передавай boolean, который вызывающий уже знал. Одна задача на класс и файл (Checkstyle: метод
   ≤ 25 строк кода без пустых и комментариев, ≤ 4 параметров, файл ≤ 300 строк, fan-out ≤ 20; PMD:
   ≤ 12 методов в классе, cognitive complexity < 10). Лимиты набора строже правил проекта и действуют
   вместо них. Область гейтов — изменённый файл целиком: большой файл сначала приводится к лимитам
   отдельной задачей без изменения поведения.
6. **Зависимости направлены к политике**, как объявлено в политике модуля
   `gauntlet/config/<module>/architecture.properties` (`./gradlew gauntletInfo` покажет, какой файл
   действует): без новых циклов и рёбер против направления, домен и прикладная логика свободны от
   транспорта и персистентности. Циклы запрещены и между компонентами, и между подпакетами одного компонента. Исключения, которые политика объявляет явно (например, унаследованный
   цикл между двумя пакетами), — долг, а не образец: новый код их не расширяет. Адаптеры вызывают прикладную
   логику и никогда не дублируют её правило.
7. **Step-определения используют каждый параметр** и проверяют наблюдаемое поведение (HTTP-ответ,
   сохранённое состояние, отправленное сообщение). Пустой step проявится как выживший Gherkin-мутант.
8. Помечай `@Tag("no-mutate")` только медленные тесты с полным контекстом или Testcontainers: они
   идут в `test`, но PIT их пропускает, и код, покрытый только ими, считается непокрытым. Держи логику
   в обычных unit-тестируемых классах; тонкие IO-адаптеры, до которых дотягиваются только интеграционные
   тесты, человек исключает через `exclude.classes`.
9. Секретам, персональным и другим чувствительным данным не место в логах, тестовых фикстурах и текстах исключений.
10. **Git.** Коммиты говорят, что изменилось и зачем, и заканчиваются `By <role>.` (coder, specifier,
    hardener…). Только новые коммиты в своей ветке: никаких `--amend`, `rebase`, `revert`, `reset` на другую
    ревизию, `checkout -B`, `push --force`, push в базовую ветку, `--no-verify` (хук блокирует). Ошибку
    исправляй новым коммитом.
11. **SOLID — по каждому принципу, не «в целом».** SRP: у класса одна причина меняться — оркестрацию,
    маппинг и IO не смешивай в одном классе. OCP: новый случай — новый класс или стратегия, а не ещё одна
    ветка `if`/`switch` по типу. LSP: реализация не ужесточает предусловия и не бросает
    `UnsupportedOperationException` вместо обещанного поведения. ISP: интерфейсы узкие — клиент не зависит
    от методов, которые не вызывает. DIP: сервис зависит от абстракции (интерфейс, порт, `List`/`Map`),
    конкретный класс выбирает конфигурация или адаптер. Измеримую часть ловит `pmdGate` (god class,
    число методов, loose coupling), остальное — `reviewer`, который называет принцип и место.
12. **Сверяйся с официальной документацией, а не с памятью — строго и на каждом шаге.** Версии языка,
    сборщика и фреймворков бери из `project.*` в `gauntlet/config/gauntlet.properties` (их показывает
    `./gradlew gauntletInfo`), а версии библиотек — из фактического разрешения зависимостей сборки
    (`./gradlew dependencies`), а не из эталонных примеров или «latest». Правило действует для всех ролей:
    `specifier` сверяет семантику протоколов и фреймворка, на которую опираются сценарии (подтверждения
    брокера, повторная доставка, коды HTTP); кодер — каждый API, аннотацию, свойство, поведение потоков,
    транзакций и таймаутов до того, как написать код; `hardener` — тестовые библиотеки; `reviewer` —
    что сверка была и источник подходит к версии. Документация — той же версии. Источники — только из раздела «Источники документации»
    ниже. Никогда не выдумывай имя свойства, атрибут аннотации, метод или поведение: нет подтверждения
    ни в одном источнике — не используй, остановись и опиши. Офлайн-источники, которые есть всегда:
    имена, типы и значения по умолчанию свойств Spring Boot — `META-INF/spring-configuration-metadata.json`
    внутри jar в кэше Gradle (`~/.gradle/caches/modules-2/files-2.1/`), сигнатуры и поведение —
    `javap -p -c -cp <jar>`. Сайт недоступен — запасные пути раздела «Источники документации» по порядку:
    javadoc-jar и sources-jar нужной версии, исходники документации по тегу, jar в кэше Gradle; каждый случай
    — в отчёт. Версии инструментов Gauntlet фиксируются в `gauntlet/config/gauntlet.properties`; JVM инструментов
    задаётся отдельно через `gate.java.version`, а локальный путь — `GAUNTLET_GATE_JAVA_HOME` или
    `-Pgauntlet.gateJavaHome` вне git, и не меняет Java приложения. Обновлять версии
    языка, сборщика, фреймворков или библиотек самого приложения ради зелёного гейта нельзя: это требует
    отдельного решения владельца и отдельной задачи. Зависимости Gauntlet держим отдельно от приложения.
13. **Антипаттерны запрещены**, не только те, что ловит `pmdGate`: god class и класс-«сервис» со всем
    подряд, логика в листенере/контроллере/планировщике вместо домена, магические строки и числа,
    boolean-параметр-переключатель, `null` вместо `Optional` или пустой коллекции, проглоченное
    исключение, `catch (Exception)` вне границы системы (листенер, планировщик, внешний клиент) или без
    решения (лог + reject/requeue/повтор/пробросить), мутабельное статическое состояние, самописный
    механизм там, где у Spring/JDK есть стандартный (retry, транзакции, валидация, конвертация, планирование, кэш).
14. **Оптимальный, безопасный и отказоустойчивый путь.** Перед реализацией назови 2–3 варианта и выбери
    с обоснованием (кратко — в отчёт). Для каждого нового пути продумай: идемпотентность обработчика
    (повторная доставка сообщения, повторный HTTP-запрос), границы транзакций (транзакция не пересекает
    вызов внешней системы), таймауты и ограниченные ретраи внешних вызовов, судьбу отказа (dead letter,
    outbox, компенсация), потокобезопасность, валидацию входа на границе, наблюдаемость (структурный лог
    без ПДн, метрика, correlation id). Кэширование закладывай сразу там, где данные читаются многократно
    и меняются редко (справочники, реестры подразделений, конфигурация внешних систем, результаты дорогих
    запросов): только стандартный Spring Cache (`@Cacheable`/`@CacheEvict`, провайдер из конфигурации),
    у каждого кэша явно заданы ключ, TTL, предел размера и инвалидация при изменении источника. Без кэша
    там, где нужна свежесть (статусы заявок, всё, что участвует в принятии решения). Самописные
    `static Map`-кэши запрещены.
15. **Читаемый код.** Имена из предметной области (заказ, счёт, клиент — не data/info/tmp);
    метод делает ровно то, что говорит имя, и держит один уровень абстракции; guard clause вместо
    вложенности; **комментариев и Javadoc в коде нет** (правило владельца 2026-10-12): код объясняет себя именами,
    неочевидные причины решений — в `<module>/docs/design.md`, простым человеческим языком, с именем класса (README
    модуля — короткий, его пишет координатор: «Правила владельца», «README модуля»); исключения — в разделе
    «Комментарии и Javadoc» `CLAUDE.md` модуля; `var` — только когда тип виден из правой
    части. Класс должен читаться сверху вниз как рассказ. **Никаких следов разработки вне рабочего контура**
    (правило владельца 2026-10-05): в коде, комментариях, тестовых фикстурах и примерах не упоминаются PR и их
    номера, GitHub, ветки, gauntlet и гейты, сессии и роли, «решение владельца», номера шагов и решений плана —
    причина правила пишется словами. То же для документов, которые уходят в контур (описание API). Правило — для
    того, что переносится в контур: `src/main`, `src/test`, сборка модуля, документы для контура. Фичи и
    `src/acceptanceTest/` в контур не уходят, а метки источников в фичах ([Ш…], PR, решения владельца) нужны
    specifier'у и человеку — их не чистят. Переключатель репозиториев в `settings.gradle`/`build.gradle`,
    `Dockerfile` и `docker-compose.yml` принадлежат владельцу: их комментарии меняются только его решением.

## Когда застрял
- Выживший мутант, который ты считаешь эквивалентным; `switch`, который должен остаться выше лимита
  CRAP; легитимная находка integrity — **остановись и опиши**. Человек может добавить исключение в
  `gauntlet/config/*-allowlist.txt`.
- Мутант RUN_ERROR вне `pit-runerror-allowlist.txt` (`mutationGate: N RUN_ERROR mutant(s) …`) — прочитай тесты
  и назови ассерт, который упал бы ровно на этой мутации. Есть такой — **остановись** и предложи человеку строку
  `Class#method Mutator # тест`; нет — это слабый тест, напиши тест, который убил бы мутанта. Падение JVM не чинится
  исключением класса из PIT и не обходится тегом `no-mutate`.
- Спецификация противоречит unit-тесту или коду — остановись и спроси; не правь ни одну сторону,
  чтобы «подружить» их.
- Ревью или координатор нашёл поведение, которое спецификация не определяет (находка типа «правило»), —
  **остановись и опиши**: какое правило решает код, какие исходы видны приёмке, варианты с рекомендацией.
  Не подбирай правило по одному случаю за раунд: следующее проявление того же пробела придёт новым
  заворотом, и гейты его не поймают — мутации закаляют тесты против спецификации, а не против
  ненаписанных правил. Решение владельца закрепляется в спецификации, затем один проход реализации
  против всего правила; накопленные регрессионные случаи становятся приёмочным набором.
- Гейт красный после 3 попыток — Stop-хук отпустит тебя с предупреждением. Работа при этом НЕ сделана:
  так и напиши в отчёте, с причинами.
